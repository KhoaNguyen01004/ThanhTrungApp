## 1. Critical — `auto-arrange` from a shipment returns HTTP 500

**`truck_load_planner/routes.py:694-719` + `truck_load_planner/models/__init__.py:113-122`**

`_get_packages_from_request()` selects the package name under an alias:

```sql
SELECT si.*, p.name AS package_name, p.length, ... FROM tlp_shipment_items si
LEFT JOIN tlp_packages p ON p.id = si.package_id
```

then hands the row to `LegacyPackage.from_row(itd)`, which reads `row["name"]`. `tlp_shipment_items` has no `name` column, so the key does not exist.

Reproduced against a copy of the live DB:

```
File "truck_load_planner/routes.py", line 713, in _get_packages_from_request
    lpkg = LegacyPackage.from_row(itd)
File "truck_load_planner/models/__init__.py", line 118, in from_row
    name=row["name"],
KeyError: 'name'
```

`auto_arrange()` has no try/except around either call site (lines 796 and 857), so this surfaces as an unhandled 500.

**This is on the primary UI path, not an API-only corner.** `static/js/truck-load-planner.js:1403` sends `shipment_id` whenever a shipment is selected:

```js
if (this.currentShipment && this.currentShipment.id) {
  payload.shipment_id = this.currentShipment.id;
} else {
  payload.packages = packages;
}
```

So "select a shipment → Auto Arrange" is broken; "no shipment → Auto Arrange" works (verified end-to-end below). The live DB currently holds 0 `tlp_shipment_items`, which is why nobody has hit it recently.

**Second defect on the same line, hidden behind the first.** Once `name` is fixed, `from_row` still does `id=row["id"]` — and `si.*` puts the **shipment-item id** in `row["id"]`, not the package id. `EnginePackage.from_legacy` then takes `getattr(source, "id")`, so every placement produced from a shipment would carry the wrong `package_id`. Fixing only the `KeyError` converts a loud 500 into silent wrong data. Fix both together.

Suggested shape (alias-consistent, no new abstraction): alias to `p.name AS name, p.id AS package_id` in the query, or build the dict for `from_row` explicitly from the package columns.

## 2. Critical — background trip refresh: `BEGIN` inside a loop leaves an open transaction

**`app/routes/trips.py:300-358`**

```python
if driver_name and driver_name != active_trip.get('driver_name', ''):
    c.execute('UPDATE vehicle_trips SET driver_name = ? ...')   # line 301

conn.execute('BEGIN')                                            # line 304
try:
    ...
    if target_name and ...:
        if target_location and is_point_in_location(...):
            ...
            conn.commit()                                        # only on arrival
except Exception:
    conn.rollback(); raise
```

Two independent ways this breaks, both reproduced on `sqlite3 3.37.2 / Python 3.10`:

**(a) The `UPDATE` on line 301 already opened a transaction.** Python's `sqlite3` in legacy isolation mode issues an implicit `BEGIN` before any DML. Line 304 then raises:

```
OperationalError: cannot start a transaction within a transaction
```

**(b) Even with no driver change, the geofence check normally doesn't fire.** A truck that hasn't arrived takes neither `commit()` branch, so the transaction opened on line 304 stays open into the next iteration, and *that* iteration's `BEGIN` raises the same error.

A faithful replica of the loop, 3 active trips, driver name changed:

```
trip 1: Error processing active trip -> OperationalError: cannot start a transaction within a transaction
trip 2: Error processing active trip -> OperationalError: cannot start a transaction within a transaction
trip 3: Error processing active trip -> OperationalError: cannot start a transaction within a transaction

left open transaction at end of loop: True
```

The error is swallowed by the per-trip handler at line 357 (`print` + `traceback`), so this is **silent**: geofence auto-advance simply stops happening. Symptom is a trip that never advances phase and never completes on its own — a dispatcher would read it as "the geofence doesn't work", not as an error.

**Knock-on: this is a concrete `database is locked` mechanism.** The uncommitted `UPDATE` from line 301 holds a `RESERVED` write lock. Nothing commits it until the first `conn.commit()` in the *second* half of the function (line ~460), which sits **after** the serial `get_route_coords()` ORS calls — one per trip, each with a server-side timeout. So a write lock on `routing_system.db` is held across N network round trips, every refresh cycle, from a background thread. This is the lock contention `CLAUDE.md` flags as "pre-existing", now with a specific cause.

> **Corrected 2026-08-06** (see `docs/CONCURRENCY_PLAN_2026-08-06.md`): this paragraph originally read "Concurrent requests block on it." That is wrong. A held `RESERVED` lock does **not** block readers — measured, four readers arriving during a 7-second hold all completed in under 5 ms. What fails is a competing **writer**, which waits out Python's default 5-second busy timeout and then raises `database is locked`. The mechanism and the fix are unchanged; only the blast radius was overstated.

Note the interaction with the existing WAL/worker decision: fixing this reduces the lock window regardless of whether WAL is enabled, so it's worth doing independently of that pair.

Suggested shape: drop the explicit `conn.execute('BEGIN')` and let the implicit transaction stand, with a single `conn.commit()` / `conn.rollback()` per iteration in a `finally` — matching how the rest of `trips.py` already handles writes.

## 3. High — `static/js/truck-load-planner.js` has zero XSS escaping

`utils.js` is loaded by `templates/truck-load-planner.html:1581`, so `UI.escapeHtml()` is available on the page. It is **never called** — the file has 0 occurrences, against 28 in `delivery-plan-builder.js`, 27 in `map.js`, 25 in `dashboard/timeline.js`. This is the one page the 2026-07-29 escaping refactor missed.

Operator-supplied text goes straight into `innerHTML`:

| Line | Sink | Source |
|---|---|---|
| 2282 | `<div class="tlp-pkg-name">${pkg.name}` | package name (`POST /api/tlp/packages`) |
| 2667 | `<span ...>${item.package_name}</span>` | package name |
| 2474-2475 | `${v.plate_number}`, `${v.vehicle_type}`, `${v.container_name}`, `${v.current_driver}` | vehicles table |
| 2549-2550 | `${s.customer_name}`, `${s.reference_number}` | shipment |
| 2719-2720 | `${p.name}`, `${p.plate_number}`, `${p.status}` | saved load plan |
| 1552, 1930 | `${r.plate_number}`, `${p._name}` | — |

With no authentication (deliberate, per `CLAUDE.md`), anything that can reach the network can persist a payload via a package or shipment name and have it execute in every dispatcher's browser on the TLP page. Severity is bounded by the internal-network deployment, but the fix is mechanical and matches the file's own dependencies — wrap each interpolation of a string field in `UI.escapeHtml()`. Non-string interpolations (`${pkg.length}`, `${item.quantity}`, `${p.id}`) don't need it.

Scanned all other JS files the same way; the remaining unescaped interpolations are numeric, boolean, or CSS-class values. No second gap found.

## 4. Medium — connection leak on the error path in `app/routes/*.py`

54 raw `sqlite3.connect()` call sites were located by AST. **One** (`app/routes/fuel.py:49`, `_compute_fuel_entry`) closes in a `finally`. The other 53 follow:

```python
try:
    conn = sqlite3.connect(config.DB_PATH)
    ...
    conn.close()
    return jsonify(...)
except Exception as e:
    return jsonify({"success": False, "message": str(e)}), 500   # conn.close() never runs
```

This violates the project's own standard (`CLAUDE.md`, Coding Standards: *"Raw `sqlite3.connect()` call sites must close the connection in a `finally`"*). CPython's refcounting collects most of these promptly, so it is not an unbounded leak — but on a **write** path an uncommitted connection can hold a `RESERVED` lock until collection, which is the same failure mode as §2 in miniature. Highest-value call sites to fix first are the write handlers: `fleet.py:107/193/251/280`, `fuel.py:414/471/553/741`, `oil.py:155/182/205/222`, `trips.py:64/178`.

**Related, separate: N+1 connections per request.** `api_fuel_log_list` (`fuel.py:225`) opens one connection, then for **each** returned row calls `_compute_fuel_entry` (1 conn), `_enrich_fuel_entry` (1), `_compute_baseline` (1-3, via `_get_normal_l_per_100km`), `_apply_anomaly_flag` → `_get_anomaly_multiplier` (1). Against the current 323 `fuel_log` rows an unfiltered `GET /api/fuel-log` opens on the order of **1,300+ connections**. Under `render.yaml`'s single synchronous Gunicorn worker, that request blocks every other one for its duration. Passing the open connection down into those helpers is a contained change that doesn't alter the DB-access-pattern split.

## 5. Low / latent

- **`services/plate_utils.py` docstring overstates uniqueness.** `normalize_plate` keeps the last 5 digits of *all* digits in the string and the docstring calls that serial "globally unique". Vietnamese plates carry a province prefix, so `50H-09473` and `51C-09473` collapse to the same key. Checked the live DB: **36 vehicles, 0 collisions, 0 short keys, and all 31 distinct `fuel_log` plates resolve** — so this is latent, not live. `_gps_by_plate_key` (`services/delivery/routes.py:69-80`) already logs and keeps-first on collision, so the delivery side degrades loudly; `services/vehicle_identity.py` should be checked for the same guard before the fleet grows. Also note a device name with trailing digits (`"51C-12345 (xe 2)"`) would silently produce the wrong key.
- **Case sensitivity is inconsistent across TTAS parsing.** `is_lost_signal()` (`ttas_client.py:216-220`) upper-cases before matching, but `_parse_speed_kmh` (`tracking_service.py:129/135`) and `normalize_vehicle` (`ttas_client.py:229-231`) use exact-case `startswith("Dừng")` / `startswith("Chạy")`. `CLAUDE.md`'s own TTAS convention says to match tolerantly on case. A cased variant from the scraper would fall through to `None`/`"unknown"` — the safe direction, but not the intended one.
- **`normalize_vehicle` orders `Dừng` before `is_lost_signal`** (`ttas_client.py:229-237`), so a hypothetical `"Dừng … MTH:…"` phrase would classify as stopped rather than lost-signal, and drop out of the No GPS filter.
- **`truck_load_planner/routes.py:262-266` (`delete_package`) leaves orphans.** It deletes only `tlp_packages`; the sibling `clear_all_packages` (271-278) also clears `tlp_placements` and `tlp_shipment_items`. Since this schema runs `enable_fk=False` with no `ON DELETE CASCADE`, nothing else catches it.
- **`DASH.map.zoomToAll()`** (`static/js/dashboard/map.js:620`) is defined but never called — dead code. If it ever is wired up, note it moves the view without calling `state.setFollowMode(false)`, unlike `focusStop` (`timeline.js:107-112`) which does.
- **`app/routes/trips.py:309`** — `if target_name and target_lat and target_lng:` treats a `0.0` coordinate as absent. Harmless for a Vietnam-only fleet; noted only because `tracking_service.py:61` handles the same case explicitly and deliberately.
